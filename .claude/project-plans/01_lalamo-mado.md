# 01 LaLaMo-Mado

## Job
Serve a Markdown file in the browser, let a human mark it up inline (comments, labels, removals, inserts, decisions), and return only the structured annotations to the agent. The file is read from disk and never re-emitted into context.

## Architecture (decided)
- **Build-raw.** Fresh codebase we own; not a fork.
- **Thin client / fat server.** Client renders, selects, anchors, and emits a stable anchor; the server owns the document model. The annotation payload is `{anchor, label, text}` (the label carries the kind — no separate `type`); the terminal decision is **document-level**, carried by the closing Submit, not a per-annotation field.
- **Integration basis: a resident local server, driven over Bash.** `edit-md serve` runs as a background process (HTTP) that lives the whole session; the agent drives it with foreground Bash subcommands (`open`, `push`) and is woken on browser events by a **backgrounded `edit-md wait`** that returns the next event from a server-side queue (→ completion notification). One proven primitive, re-armed per event — no websocket in the agent sync. This is the integration spine from day one.
- **Backend: .NET 10 (LTS).** Hosts the server and the document model; shipped self-contained single-file, published per target RID.
- **Cross-platform (hard requirement).** Runs on Windows, Linux, and macOS. No Windows-only APIs; per-OS concerns — browser launch, per-RID self-contained publish, code-signing / notarization — are handled explicitly, not assumed away.
- **Single session.** One session services its own open document(s). No cross-session sharing.
- **Live reply — threaded, in scope.** The agent can push a reply that renders in-page against a span, one thread per annotation (02). In-page reply is a kept feature, within the single session.
- **Rendering: rich base.** Markdown → sanitized HTML, code highlighting, and **mermaid** as the diagram baseline.
- **Client ships pre-built.** Static assets built at dev time; the target PC runs no client build. We nonetheless **positively encourage AI-powered users to tailor the client** — cosmetics and behaviour — to their own preference, and ship it **structured to be separable to the degree feasible** so that tailoring is easy.

### Client / server split
Client owns (irreducible): selection → character offsets, highlight anchoring through re-render, the comment popover, rendering markdown/mermaid/katex/code to a selectable DOM. Server owns (fat): parse → block model → authoritative source-line map, diff / change-gutter, label/response-kind config, persistence + content-hash validation, export. Wire contract is `{anchor, label, text}` — the client never ships its block model back.

## Feature set
Want-levels: **MUST** · **WANT** · **NICE**.

**Core review loop**
- MUST — serve a `.md` locally, auto-open; heartbeat → graceful shutdown on tab close.
- MUST — read from disk; return only annotations; never re-emit content. (The bar is on pointlessly re-shuffling the same content back across the boundary — not on deliberate on-demand reads or the compact document map, which are legitimate.)
- MUST — click a selected span → comment surface opens directly (no context-menu detour).
- MUST — highlight anchoring survives re-render and scroll (the hard core).
- MUST — document-level ("General") annotations.
- MUST — **Submit is the deliberate end**: it closes the page; closing the tab without it is an **abort**. Three exits: **Approve** (no annotations) · **Apply & review** (agent applies the notes, then re-opens the revised version in a new tab for another round — diff per C) · **Apply silently** (agent applies, no further round). Plan 11 will replace the closing with an end card that stays until its big Close button (decided 2026-11-04).
- MUST — mid-read sends that keep the review open: **Send now** = one query, answered in the page (a reply is for exactly one query); **Send drafts (N)** = the drafts so far as one coherent silent group, gated on N > 0. Submit carries only what no send delivered.
- WANT — content-hash validation (detect the file changing under the review).

**Labels / response kinds**
- MUST — a single comment/annotation surface with a **simple, easily-customizable set of icon-meaning labels** that merely prefix the comment (the client is meant to be tailored easily). **Remove** and **Insert** are just two such labels, **not** separate first-class modes.
- NICE — multi-select spans across the doc — chiefly to **group related information together for the AI**, not merely to apply one label at once. Skipped for now: Send drafts (N) delivers a coherent group (01b).

**Diff & decisions**
- Highlights are **nestable by design** — a span can carry an annotation and a decision at the same time (stacked highlight colours), not one or the other.
- WANT — per-open snapshot + change-gutter (what moved since the last open), reliable through re-render; the **diff is computed server-side** to offload the client and the agent as much as possible.
- WANT — **AI-authored decision flags**: the agent marks spans needing a human call, delivered as a sidecar alongside the md.
- WANT — feedback-notes re-review loop: a note per change pops in place on re-open.
- NICE — agent-proposed fixes the reviewer picks inline (radio/checkbox); AI-driven, but the payload/API formalizes the pick.

**Layout & chrome**
- MUST — panels dock; never occlude text; only the comment popup, the reply panel and short-lived choosers (the label palette, the skill picker) may overlap. The questionnaire card (11) is the one named exception, and folds to its chip whenever the comment popup opens.
- MUST — Esc closes the topmost thing: picker or palette, then comment popup, then reply panel, then an armed label.
- MUST — the **left pane is a single filterable panel**: a scroll-tracked TOC (per-section annotation-count badges) with changes and decisions mashed in under their chapter; a per-category checkbox toggles each of TOC / changes / decisions (default all on). Seek results list there as selectable set rows (see Later).
- WANT — information-dense, tweakable layout (spacing, dock-side configurable).
- WANT — theming via CSS variables + user config; the persisted theme switcher tucks under a small side **settings** icon (room for this area to grow).
- WANT ✅ — **dedicated review window**, grouped window-per-session: one session → one window, each doc → a tab in that window — landed with a dedicated Chromium profile (see 01c), never the user's everyday browser window.
- NICE ✅ — dedicated browser-profile launcher (same).

**Rendering**
- MUST — markdown → sanitized HTML (dompurify); code highlight (highlight.js).
- MUST — mermaid diagrams (baseline), annotatable.
- WANT — katex math (offline fonts); display formulas annotatable as a whole.
- NICE — image annotations; export feedback as markdown; export / re-import JSON to resume a review.

**Integration**
- MUST — a self-contained harness entry of its own: a dedicated skill + bin (**`edit-md`**), **completely separate** from the existing `show-md-for-comment` → md-annotator flow in both implementation and harness. Nothing shared — no common skill, bin, or code.

### Non-goals
Blob-patch-over-built-bundle as the customization mechanism; an in-repo annotate plugin; IDE-integration entry; a **WYSIWYG AI-powered editor / live synchronizer** — the parked idea this product is explicitly *not*.

## Scope
### In
- The single-session annotate-and-return loop over the resident server.
- Robust highlight anchoring that survives re-render.
- **Threaded in-page live reply** (02) — the agent pushes a reply that renders against a span; additive to the one-shot Submit/Approve, which stays the primary exit; a reply never re-opens or replaces the document.
- **Mic dictation (voice in)** — speak a comment into the field; client-side (Web Speech API), Ctrl+D toggle, cs-CZ/en-US. ✅ Landed and validated 2026-11-02 (plan 03, retired — see below).

### Later (in scope, deferred)
- **Conversation side-channel** — fire ad-hoc messages to the agent while you keep reading; the agent works them in parallel and replies in place. Extends the single-thread reply; additive to Submit/Approve, never replaces the document. ✅ Landed and validated 2026-11-09 (plan 02, retired — see below).
- **AI-assisted seek** — the user enters an arbitrary natural-language query; the agent returns a set of lines to highlight ("Ctrl+F, but clever"). Several seeks can coexist over one doc; each result becomes a selectable item that rolls out its distinct findings, each clickable and navigable. ◐ The agent answers a seek with a set of marks (01c step 5), listed as its own selectable row in the left pane — first used in lorem round 10 (all verbs); no separate Seek tab (decided 2026-11-04). Open: a dedicated way to ask (today a comment; plan 11's *Custom…* if built).
- **Block table** — an explicit table of the document's blocks and a `blockId` in the payload, for a document map (01d). Postponed until needed (decided 2026-10-26; carried from 01b, retired 2026-11-09): the agent has worked from `lines` with no case lacking a block id.
- **Read-aloud (voice out)** — hear a chapter spoken with a word-tracking highlight; client-side (Web Speech `speechSynthesis` boundary events). From plan 04. **Deprioritized — unlikely to be worth much** (reading is faster anyway); kept only as a stretch.

### Out of scope
- **Dictation term-accuracy** — a Claude Code hooks/glossary feature about dictating *prompts to the agent*; a separate concern, not part of this product.

## Open (not yet decided — kept separate from the decided set above)
_None outstanding at the roadmap level; remaining open items live in the phase plans._

## Implementation steps
Split into four gated phases, each its own plan file; each step ends at a verifiable gate.
- **A — walking skeleton**: resident server + Bash drive + harness-wake round-trip. **Validated 2026-10-26**; its plan `01a_walking-skeleton.md` is retired to git history (`git log -- .claude/project-plans/01a_walking-skeleton.md`). Carried notes:
  - Delivery is acknowledged, not assumed: `/api/next` marks an event `taken` with a 10 s lease; `wait` prints it, then `POST /api/ack {seq}` makes it `delivered` (and pushes "with agent ✓" to the page). A `wait` killed in between lets the lease run out and the event goes to the next `wait` — at-least-once, so the skill tells the agent to skip a `seq` it already handled.
  - Distribution: built on the user's PC by `onboarding/install.ps1`. Prebuilt per-RID zips only when someone without the .NET SDK needs them; no build-time configurability.
  - `serve` is keyed by `CLAUDE_CODE_SESSION_ID`, which changes on `/clear`: a second server starts and the first lingers until session end — accepted.
  - Permission prompts during a review: `allowed-tools` grants last one turn, so they can't cover the wake-ups; the user approves "don't ask again" — no settings change shipped.
  - Cross-OS: built and e2e-tested on Windows only; macOS/Linux is postponed until someone working on that OS drives it.
- **B — core annotation**: select → anchor → comment → return; anchoring that survives re-render. **Validated 2026-11-09**; its plan `01b_core-annotation.md` is retired to git history. Carried notes:
  - Every Markdig block carries `data-src-start/-end`. The client sends a text-quote anchor plus the enclosing blocks' source range; the server finds the quote there verbatim, else through a plain projection of the source (inline markup, link targets, block markers, fences and table rules dropped, each char keeping its offset) → `{lines, sourceStart, sourceEnd, exact}`. `exact: false` only when even that fails, and `lines` are then the block's. List markers are stripped only where Markdig found a list item.
  - An insert point at a span's end lands after its closing syntax. Highlights use the CSS Custom Highlight API, with no wrapper elements. The agent gets 1-based `lines`, not a block id. Drafts persist per server instance in `localStorage`. Ids in rendered documents and replies carry an `md-` prefix, so a heading cannot take a page element's id.
  - Block pick: Alt outlines the block under the pointer, and Alt+click opens the popup on it (`scope: "block"`); a table row is the smallest part of a table. Ctrl+C on a selection copies it while the comment box has focus.
  - Decided not to build: keyboard-only selection, and several spans grouped into one annotation (Send drafts covers it).
- **C — layout, rendering, diff & decisions** ([01c_layout-render-diff.md](01c_layout-render-diff.md)): the docked review surface; **mermaid/katex are lazy-loaded** (decided); server-computed diff; nestable highlights.
- **D — live reply, side-channel, seek, voice** ([01d_live-voice-seek.md](01d_live-voice-seek.md)): the interactive layer, built last on the A–C spine.

**Validated 2026-11-02 and retired to git history** (`git log -- .claude/project-plans/<file>`). Carried notes:

Replies bind to their annotation and open from the highlight's small card or the right pane, which filters to replies only. A thread is the first annotation, the agent's replies and the reviewer's follow-ups: Reply on any agent reply opens the ⤢ panel as the thread's chat (`client/thread.js`, moved and sized by `client/floating.js`); a follow-up always goes as Send now with `replyTo` the thread's first id, has no card, badge or place in Submit, and the agent answers it with `push --to` that id. `edit-md thread <docId> <id>` prints the turns on demand (`Server/ReviewThreads.cs`); a reply to no annotation is a thread of its own, `r<seq>`.
- `12_skill-picker.md` (retired 2026-11-09, approved in real use 2026-11-05 and 2026-11-09) — the server reads the skills itself, never through the agent's context (`Server/SkillCatalog.cs`, `edit-md skills <docId>`, `GET /api/docs/{docId}/skills`): USER from `~/.claude/skills/`, REPO from `.claude/skills/` in the git root and every folder down to the document's, with `.claude/commands/**/*.md` as skills named by path with `:` segments. A named skill never fires by itself. The session invokes it when the comment asks, follows a user-only one only if already run in the session, and otherwise asks for it to be typed once. A repo-context run fires a `/name` that starts the comment, user-only ones included, and never one from a brief. A blank run loads no skills.
- `14_spoken-or-typed.md` (retired 2026-11-09, approved in real use 2026-11-04 and 2026-11-09) — the page tags each character of a comment as `mic` or `key`, invisibly (`client/spoken.js`, synced by common prefix and suffix; text brought back by undo counts as `mic` when the comment holds any dictation), and the wire carries `spokenRanges`. - `13_label-stamp.md` (retired 2026-11-16, approved in real use 2026-11-05, 2026-11-09 and 2026-11-11) — a label is armed from the palette (Ctrl+Shift tapped, or 🏷: a centred grid of every label with its digit, the description on hover), by Alt+digit (`hotkey` 1–9 in the labels contract; 👍 on 5, 👎 *Not this* on 6; a clash is listed as a problem), or by Ctrl+Shift tapped twice within half a second, which re-arms the last label (`client/stamp.js`).
