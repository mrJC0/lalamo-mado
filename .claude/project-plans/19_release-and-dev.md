# 19 Release and dev — the deployed edit-md beside the one being built

## Goal
The released edit-md serves every project on this PC, while this repo builds and tries the next one, and neither can see or disturb the other.
Think VS Code and VS Code Insiders: one product, two builds, each with its own home, state, ports and window.
Both can run in the same Claude Code session: `/edit-md` to review a plan, `/edit-md-dev` to try the feature it describes.

## Where they collide today
- **The server is found by session alone.** `server.json` lives in `<temp>/edit-md/<session id>/` (`ServerState.cs`), so in a session already running the released server, a dev binary's `serve` answers *already-running* and every later dev command talks to the released server.
- **The port is derived from the session alone** (`StablePort.cs`): whichever server starts second takes a neighbour port, so the origin, and with it the page's localStorage, depends on start order.
- **Your own files are shared**: labels, send buttons, glossary and the page overlay in `~/.claude/edit-md/`.
  The overlay holds copies of released page files, which the server serves before the dev page's own; and trying *new-kind*, *customize-page* or *remember a correction* in dev writes into your real files.
- **There is one home.** Trying a build means installing it over the release (`install.ps1` stops the released servers of every session), or running `bin/Debug`, which still collides on the server state above.

Already separate per install folder: browser profiles (so each build gets its own window), `prefs.json`, `last-seen/`.

## The split: a channel baked into the build
The build carries its channel, `release` or `dev`, as assembly metadata (`-p:EditMdChannel=dev`), so the binary knows what it is without an environment variable on every call.
Everything else follows from it:

| | release | dev |
|---|---|---|
| binary home | `~/.claude/bin/edit-md/` | `~/.claude/bin/edit-md-dev/` |
| skill | `/edit-md`, personal (`~/.claude/skills/edit-md/`) | `/edit-md-dev`, this repo only (`.claude/skills/edit-md-dev/`) |
| server state | `<temp>/edit-md/<session>/` | `<temp>/edit-md-dev/<session>/` |
| ports | 41000–41999, as today | 42000–42999 |
| browser profiles, `prefs.json`, `last-seen/` | in its home | in its home, so its own window |
| your labels, buttons, glossary, page overlay | `~/.claude/edit-md/` | `~/.claude/edit-md-dev/` |
| Whisper models | `<home>/whisper/` | its own if present, else the release's, read-only |
| repo files `<git root>/.claude/edit-md/` | shared | shared |
| tells you which | — | a **DEV** badge in the top bar with the commit on hover, `[dev]` in the tab title |
| built from | a named commit | the working tree |

The release keeps every path, port and origin it has today, so its settings, open tabs and microphone grant carry over.

## Deploying
- **Dev:** `pwsh scripts/deploy-dev.ps1` publishes the working tree into `~/.claude/bin/edit-md-dev/` and stops only dev servers.
  It also writes the dev skill (below).
  The first deploy copies your labels, buttons, glossary and pc settings into the dev homes once; `-Reseed` copies them again. The page overlay is never copied.
- **Release:** `pwsh onboarding/install.ps1 -Ref <commit or tag>` builds that commit in a temporary git worktree, so uncommitted or half-done work never reaches the release, and the binary and its SKILL.md come from the same commit.
  Without `-Ref` it installs the checkout as today, which is what a new user does.
- Promoting dev to release is that one command, run when you choose; like any update, it stops the released servers.

## The dev skill: `/edit-md-dev`
- Generated by `deploy-dev.ps1` from `onboarding/skills/edit-md/SKILL.md`, the way `install.ps1` already rewrites the binary path for a custom tool home: paths point at the dev homes, the name and description say dev.
  Git-ignored, so the skill always matches the deployed dev binary, even while the working copy's SKILL.md is ahead of it.
- On top, a short head: *the dev build of edit-md, deployed from `<commit>` at `<time>`; if `src/` or the skill changed since, run `pwsh scripts/deploy-dev.ps1` before `serve`*.
- User-invoked, like `/edit-md`; different names, so neither shadows the other.

## Decisions
- **Channel baked in at build, not an environment variable.** In this repo `/edit-md` and `/edit-md-dev` run in one environment, so a variable set for dev would mislabel the released binary too.
- **Two channels, not arbitrary instance names.** Nothing needs a third; a worktree build deploys into the same dev home.
- **Dev keeps its own copy of your files** rather than reading the released ones: isolation is the point, and the overlay alone would break the dev page.
- **The repo's `.claude/edit-md/` stays shared.** It belongs to the document's repo, and whatever dev writes there shows in `git status`.
- **The dev skill is generated, not hand-written.** A hand-written one that says "follow the working copy's SKILL.md with these paths swapped" would describe commands the deployed binary may not have yet, and leaves the path swap to the agent on every call.
  It would also fade: after a compaction Claude Code re-attaches the invoked SKILL.md, not the files it pointed to.

Settled while building (2026-11-23):
- **The commit comes from `publish.ps1`, not from SourceLink.** It passes `git describe --always --dirty` as `-p:EditMdCommit`, so a dev build from a changed tree says `-dirty`, which the SDK's own revision stamp never does; a plain `dotnet build` reports `commit unknown`.
- **A build without `-p:EditMdChannel` is the release**, Debug included, so `install.ps1` and every existing e2e script behave as before; only `deploy-dev.ps1` makes a dev build. Defaulting Debug to dev was weighed and dropped: the e2e scripts check the user files under `<claude home>/edit-md/`.
- **The e2e check uses a fake browser** that records each launch: two `--user-data-dir`s and two `--new-window`s prove two windows without flashing real Chrome on the screen, as `grouping.mjs` already does for one build.
- **`-Ref` hands over to the named commit's own `install.ps1`**, so an older commit installs exactly as it did then; the worktree goes in a `finally`.

## Built
- `BuildChannel` (`src/LalamoMado/BuildChannel.cs`) reads the channel and commit from assembly metadata and derives the state root, user-files folder, default tool home and first port; `ServerState`, `StablePort`, the labels, send buttons, glossary and overlay paths, and the Whisper fallback read it.
- `status`, `serve`'s *listening* and *already-running* lines, and `help`'s last line (`Build: dev, commit 9b88de6-dirty`) carry channel and commit; the page view carries them to the DEV badge and the `[dev]` title.
- `scripts/publish.ps1 -Channel`, `scripts/deploy-dev.ps1`, `onboarding/install.ps1 -Ref`; READMEs say how to deploy dev and promote a commit.

## Side topic: a session's tabs in one window
The window per session landed in 01c, but gaps remain; pinned down here, then moved to a plan of its own.
What the code suggests, to confirm against what you saw:
- **After a server restart** in the same session (`stop` then `serve`, or `server-stopped`), the new server knows no documents, so its first `open` passes `--new-window`: a second window beside the old one with its dead tabs.
- **While the only tab is disconnected** (sleep, a `lost` page), the next `open` also counts the session as windowless and starts a new window.
- **A tab dragged into a window of its own** probably catches the later tabs, since Chrome opens them in the profile's last focused window.
- **A resumed conversation** may get a new session id and with it a new profile and window — to check.
- **With this plan**, a session using both builds has two windows, release and dev — intended, told apart by the DEV badge.
